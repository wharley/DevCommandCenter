# v0.1.31 Release Notes

## Highlights

- Reworked delegation so it starts from the composer instead of a configuration
  dialog, turning a six-field form into a single click on a target agent.
- Mode and context policy are now derived from what the DCC already knows, while
  the effort and fast-mode dials chosen in the composer travel to the delegated
  session.
- Delegation cards show the decisions taken for each run, and finished read-only
  delegations can be replayed on another agent.
- Plan handoff runs directly from an approved plan instead of reopening a
  prefilled form.

## Delegation From the Composer

- The Send button carries a menu of eligible target agents. Picking one delegates
  the current composer draft immediately, using the target's recommended model.
- `Can edit files` turns the run into an implementation delegation and narrows the
  target list to agents that support edits.
- `Delegate to several` sends the same task to multiple agents at once, each in
  its own child session, so their answers can be compared.
- The session header control and the command palette entry now open this menu
  rather than a dialog, so delegation has a single path.
- Failed delegations keep the composer draft, so an instruction rejected by the
  clean-worktree preflight can be retried after committing.

## Decisions Are Derived, Not Asked

- Implementation delegations use full reanchor context.
- Read-only delegations review the current diff when the worktree has changes,
  and explain the code when it is clean.
- Reasoning effort and fast mode are no longer hardcoded for delegated sessions;
  they follow the composer selection.

## Delegation Cards and Reruns

- Cards display mode, target agent, context policy, and edit permission as chips
  alongside the run status.
- A finished read-only delegation can be replayed on a different agent. The
  rerun sends the stored prompt verbatim so both runs receive the same task and
  context.
- Implementation delegations are excluded from reruns because their prompt pins
  a child worktree that is removed on apply or discard.

## Plan Handoff

- `Delegate implementation` starts the delegation directly with the approved
  plan, implementation criteria, and an edit-capable target resolved from the
  provider catalog.
- Plan approval remains the human checkpoint, and the clean-worktree preflight
  still guards the run.

## Internals

- Added `delegation-defaults`, `delegation-targets`, and `delegation-decisions`
  as pure modules with unit coverage for mode derivation, target eligibility,
  and rerun rules.
- Moved `ManualDelegationRequest` to `delegation-request` and removed
  `delegation-dialog`.
- Collapsed `delegation.dialog.*` translations into `delegation.contextOptions`,
  still used by the delegation and approval cards.
- Updated `docs/DELEGATION_AGENTS.md` to describe the current flow.

## Known Gaps

- Delegation is offered while the parent session is idle. Delegating during an
  active parent run is not available yet.
- Fan-out results are shown as separate cards in the thread; there is no
  combined view of what the targets agreed on.
- The delegation surface was validated through type checks, unit tests, and
  builds rather than an interactive pass.

## Validation Before Publishing

- Run desktop type checks: `yarn workspace @dcc/desktop typecheck`
- Run the complete desktop test suite: `yarn workspace @dcc/desktop test`
- Build the desktop application: `yarn workspace @dcc/desktop build`
- Build the mobile web application: `yarn workspace @dcc/mobile-web build`
- Run the Rust workspace tests: `cargo test --workspace`
- Check the Tauri crate: `cargo check --manifest-path src-tauri/Cargo.toml`
- Confirm release metadata is `0.1.31` in `package.json`,
  `sidecar/package.json`, `sidecar/src/index.mjs`, `src-tauri/Cargo.toml`, and
  `src-tauri/tauri.conf.json`.
